### Testing Strategy

[Source: docs/architecture/12-lean-testing-strategy.md]

**Philosophy**: Confidence over coverage. Focus on high-value integration tests for critical user flows.

**Testing Pyramid (Simplified):**

1. **Unit Tests (Small Base)**: Only for critical, isolated business logic (scoring algorithms, complex transformations)
2. **Integration Tests (High-Value)**: Validate end-to-end user flows, ensuring main components (grammY, Supabase) are connected

**What NOT to do:**

- No automated E2E testing (manual Telegram testing sufficient)
- No strict naming conventions (logical names only)
- No chasing coverage metrics (confidence-driven)

**Test Requirements for Story 1.3:**

- Minimum 2 integration tests covering existing features (webhook validation, book addition)
- Tests should validate component integration, not just unit logic
- Use Deno Test Runner exclusively

### CI/CD Pipeline Design

[Source: docs/architecture/10-simplified-development-and-deployment-workflow.md]

**Guiding Principles:**

- Solo-developer productivity (minimize friction)
- Lean & effective (simplest tools necessary)
- "Shift-left" quality (catch bugs locally before push)

**Local Workflow (Husky):**

1. **On `git commit`**: Prettier, ESLint, Deno fmt, Deno lint run automatically
2. **On `git push`**: Full Deno test suite runs to catch functional bugs

**CI/CD Workflow (GitHub Actions):**

**CI Pipeline (on Pull Request):**

- Trigger: PR opened/updated to any branch
- Steps:
  1. Checkout code
  2. Install Deno
  3. Run `deno lint`
  4. Run `deno fmt --check`
  5. Run `deno test -A` (full test suite)
- Result: PR blocked if any step fails

**CD Pipeline (on merge to main):**

- Trigger: Push to `main` branch
- Steps:
  1. Checkout code
  2. Install Supabase CLI
  3. Authenticate with Supabase (using GitHub Secrets)
  4. Deploy Edge Functions: `supabase functions deploy`
- Result: Automatic deployment to production

**Rollback Strategy:**

- Revert problematic commit in Git
- Automatic re-deployment of previous stable version

### Supabase CLI Deployment

**Command**: `supabase functions deploy`

**Prerequisites:**

- Supabase CLI installed
- Authenticated with `supabase login` or access token
- Project linked or PROJECT_ID specified

**Deployment Flags:**

- `--project-ref <project-id>` - Specify target project
- `--no-verify-jwt` - Optional: Skip JWT verification for testing

**Example GitHub Actions deployment step:**

```yaml
- name: Deploy to Supabase
  run: |
    supabase functions deploy --project-ref ${{ secrets.SUPABASE_PROJECT_ID }}
  env:
    SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}
```

### Known Issues

#### PostgREST Schema Cache Timing (Environmental - Not Blocking)

**Issue**: The "Database - Lookup tables populated" test intermittently fails with `PGRST205: Could not find the table 'public.genres' in the schema cache`.

**Root Cause**: PostgREST's schema cache doesn't refresh immediately after `supabase db reset`. Tables exist in PostgreSQL and are accessible after a brief delay (verified via direct API call).

**Impact**: Low - This is an environmental timing issue in local development. The test has proper retry logic (5 attempts with exponential backoff). Tables work correctly in production and via direct queries.

**Evidence**:

- Direct curl to PostgREST endpoint succeeds: `http://127.0.0.1:54321/rest/v1/genres` returns 10 genres
- Test only fails immediately after database reset
- Not a production concern - only affects rapid local test execution

**Recommendation**: Document as known limitation or add longer initial delay. Not blocking for story completion as it's infrastructure-related, not code quality.
