# Story 2.3: Post-Read Reflection

## Status

Draft

## Story

[Epic Reference: docs/epics/epic-2-ai-intelligence-user-interaction.md - Story 2.3]

**As a** reader who has just finished a book,
**I want** the bot to guide me through a reflective conversation about my reading experience,
**so that** my detailed thoughts and opinions are captured to improve future recommendations and build my reading profile.

## Acceptance Criteria

1. When a book's status changes to 'finished', the system automatically triggers the reflection workflow.
2. The bot sends a proactive message inviting the user to reflect (e.g., "I see you finished _Book Title_! Would you like to reflect on it?").
3. The workflow is a stateful, multi-step conversation managed by LangGraph, guiding the user through at least 3 distinct reflection questions.
4. User responses are saved to the `reflections` table, linked to the correct book.
5. The conversation state is persisted in the `conversational_state` table, allowing the user to pause and resume.
6. Upon completion, the bot sends a confirmation message summarizing the captured reflections.
7. The workflow must be covered by an automated integration test that passes in the CI pipeline.
8. The LangGraph state machine must include error handling for invalid user inputs or unexpected state transitions.

### LangGraph Implementation Strategy

**Decision: Use LangGraph for Stateful Conversation Orchestration** [Source: docs/architecture/ai-orchestration-architecture.md#When-to-Use-LangChain/LangGraph]

**Rationale**:
- Story 2.3 requires stateful, multi-step conversation workflow (perfect use case for LangGraph)
- Need to persist state between user messages (pause/resume capability)
- Complex branching logic: question progression, error handling, retry logic
- LangGraph provides built-in checkpointer for state persistence

**Architecture Pattern** [Source: docs/architecture/ai-orchestration-architecture.md#Post-Read-Reflection-Complex-LangGraph]:

```mermaid
graph TD
    A[User: "Finished reading X"] --> B[Start Reflection Workflow]
    B --> C[Flash: Generate Initial Questions]
    C --> D[Gather User Responses]
    D --> E{More Questions?}
    E -->|Yes| C
    E -->|No| F[Pro: Deep Analysis]
    F --> G[Update Preference Model]
    G --> H[Pro: Generate AI Rating]
    H --> I[Store Results & Complete]
```

**Note**: Story 2.3 implements A → E (reflection questions and response capture). Story 2.4 implements F → I (AI analysis and preference updates).

**LangGraph State Machine Design**:

1. **Nodes**: start → ask_question → process_response → (loop or finalize) → end
2. **State Persistence**: Use PostgreSQL checkpointer (store in conversational_state.state_data JSONB)
3. **Thread ID**: Use Telegram chat_id as thread identifier for checkpointer
4. **Error Handling**: error_node with retry logic (max 3 retries per question before skipping)
5. **Conditional Edges**: Based on current_question index and response validation

**Performance Guidance** [Source: docs/architecture/ai-orchestration-architecture.md#Performance-Guidance]:

- Tree-shake imports: `import { StateGraph } from "@langchain/langgraph";` (NOT `import * as langgraph`)
- Lazy-load LangGraph modules only when reflection workflow is triggered
- Cold start target: <3s for reflection-processor function
- Warm invocation target: <500ms for state transitions

**Observability** [Source: docs/architecture/ai-orchestration-architecture.md#Observability]:

- Use structured logging for all state transitions: `logger.info("LangGraph state transition", { from, to, chat_id, book_id })`
- Optionally enable LangSmith tracing for debugging (set LANGCHAIN_TRACING_V2=true in dev environment)
- Log checkpointer operations: state save/load, checkpoint expiry

### Database Trigger Strategy

**Trigger Implementation** [Source: docs/architecture/data-models-and-schema-changes.md]

Create PostgreSQL trigger to detect status change to 'finished':

```sql
CREATE OR REPLACE FUNCTION trigger_reflection_workflow()
RETURNS TRIGGER AS $$
BEGIN
  -- Only trigger if status changed TO 'finished' (not already finished)
  IF NEW.status = 'finished' AND OLD.status != 'finished' THEN
    INSERT INTO book_events (book_id, event_type, event_data)
    VALUES (
      NEW.id,
      'reflection_requested',
      jsonb_build_object(
        'title', NEW.title,
        'author', NEW.author,
        'user_date_finished', NEW.user_date_finished
      )
    );
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER books_status_finished_trigger
AFTER UPDATE OF status ON books
FOR EACH ROW
EXECUTE FUNCTION trigger_reflection_workflow();
```

### Technical Constraints

**LangGraph Checkpointer Selection** [Source: @langchain/langgraph docs, verify with Context7]

Options for state persistence:
1. **PostgreSQL Checkpointer** (RECOMMENDED): Native Supabase integration, stores in conversational_state table
2. **Memory Checkpointer**: In-memory only, not suitable for multi-user or stateful workflows
3. **Custom Checkpointer**: Implement BaseCheckpointSaver interface if needed

**Decision**: Use PostgreSQL Checkpointer with conversational_state table as storage backend.

**State Timeout Extension** [Source: supabase/functions/_shared/conversational-state.ts:32]

Current timeout: 15 minutes (STATE_TIMEOUT_MINUTES = 15)

**Consideration**: Reflection workflows may take longer than 15 minutes if user is interrupted. Options:
1. Extend timeout to 60 minutes specifically for reflection workflows
2. Add logic to extend TTL on each user interaction
3. Allow users to manually resume expired workflows via /reflect command

**Recommendation**: Implement option 2 (extend TTL on each message in reflection workflow).
