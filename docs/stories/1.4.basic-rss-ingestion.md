# Story 1.4: Basic RSS Ingestion

## Status

Ready for Review

## Story

**As a** solo developer,
**I want** automated RSS ingestion from my Goodreads "read" shelf,
**so that** newly finished books are automatically added to the ShelfHelp database without manual data entry.

## Acceptance Criteria

1. A scheduled job (pg_cron) runs daily to fetch the Goodreads RSS feed for the "read" shelf
2. The system parses the RSS XML and extracts all relevant book fields (title, author, ISBN, Goodreads ID, user rating, dates, etc.)
3. New books detected in the RSS feed are automatically inserted into the `books` table
4. Existing books (matched by `goodreads_id`) are updated with any changed data (e.g., user moved book to "read" shelf, added rating)
5. The RSS ingestion service handles errors gracefully (network failures, malformed XML, missing fields) and logs all activity
6. Integration tests validate the RSS parsing logic and database insertion/update operations
7. Documentation explains how the RSS ingestion works and how to monitor/troubleshoot it

### Data Models

[Source: docs/architecture/4-data-models-and-schema-changes.md]

**`books` Table Schema (Relevant Fields for RSS Ingestion):**

```sql
CREATE TABLE books (
    -- Core Identifiers
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    goodreads_id INTEGER UNIQUE,  -- PRIMARY MATCH KEY for upserts
    isbn TEXT,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT now(),

    -- Bibliographic Data
    title TEXT NOT NULL,
    author TEXT NOT NULL,
    page_count INTEGER,
    publisher TEXT,
    publication_date DATE,
    series_name TEXT,
    series_number INTEGER,
    cover_image_url TEXT,
    goodreads_link TEXT,

    -- User Data (from Goodreads RSS)
    user_shelves TEXT[],  -- Array of shelf names
    user_rating INTEGER CHECK (user_rating >= 1 AND user_rating <= 5),
    user_date_added TIMESTAMP WITH TIME ZONE,
    user_date_finished TIMESTAMP WITH TIME ZONE,

    -- System Data
    status TEXT CHECK (status IN ('to_read', 'currently_reading', 'finished', 'dnf'))
);
```

**RSS Feed to Database Field Mapping:**

| RSS XML Field        | `books` Table Column     | Notes                                       |
| -------------------- | ------------------------ | ------------------------------------------- |
| `<book_id>`          | `goodreads_id`           | Unique identifier, used for upsert matching |
| `<title>`            | `title`                  | Required field                              |
| `<author_name>`      | `author`                 | Required field                              |
| `<isbn>`             | `isbn`                   | May be empty                                |
| `<book_published>`   | `publication_date`       | Parse as DATE                               |
| `<book><num_pages>`  | `page_count`             | Nested element                              |
| `<book_image_url>`   | `cover_image_url`        | Use largest available image                 |
| `<link>`             | `goodreads_link`         | Book review link                            |
| `<user_rating>`      | `user_rating`            | 1-5 scale, may be 0 if not rated            |
| `<user_read_at>`     | `user_date_finished`     | Parse as TIMESTAMP                          |
| `<user_date_added>`  | `user_date_added`        | Parse as TIMESTAMP                          |
| `<user_shelves>`     | `user_shelves`           | Parse as TEXT[] array                       |
| `<book_description>` | `ai_summary` (temporary) | Can be used until AI enrichment is added    |

**Upsert Logic:**

- **Match Key**: `goodreads_id` (unique constraint)
- **Insert**: If `goodreads_id` not found in database
- **Update**: If `goodreads_id` exists, update all fields from RSS feed (allows detecting shelf changes, rating updates)

### RSS Feed XML Structure

[Source: User-provided Goodreads RSS feed analysis]

**Feed URL Format:**

```
https://www.goodreads.com/review/list_rss/{user_id}?key={private_key}&shelf={shelf_name}
```

**Environment Variable**: `GOODREADS_RSS_FEED_URL_READ`

**XML Structure Per Book Entry:**

```xml
<item>
  <guid>https://www.goodreads.com/review/show/...</guid>
  <pubDate>Sun, 01 Jan 2025 00:00:00 -0800</pubDate>
  <title>Book Title</title>
  <link>https://www.goodreads.com/review/show/...</link>
  <book_id>12345678</book_id>
  <book_image_url>https://...</book_image_url>
  <book_small_image_url>https://...</book_small_image_url>
  <book_medium_image_url>https://...</book_medium_image_url>
  <book_large_image_url>https://...</book_large_image_url>
  <book_description><![CDATA[...]]></book_description>
  <book>
    <num_pages>350</num_pages>
  </book>
  <author_name>Author Name</author_name>
  <isbn>1234567890</isbn>
  <user_name>User</user_name>
  <user_rating>4</user_rating>
  <user_read_at>Sun, 01 Jan 2025 00:00:00 -0800</user_read_at>
  <user_date_added>Wed, 15 Dec 2024 10:30:00 -0800</user_date_added>
  <user_date_created>Wed, 15 Dec 2024 10:30:00 -0800</user_date_created>
  <user_shelves>read, favorites</user_shelves>
  <user_review><![CDATA[...]]></user_review>
  <average_rating>4.2</average_rating>
  <book_published>2020</book_published>
  <description>...</description>
</item>
```

**XML Parsing Notes:**

- Use `npm:fast-xml-parser` (Deno-compatible via npm specifier)
  - Handles CDATA sections with `cdataPropName` option
  - Pure JavaScript, no C/C++ dependencies
  - Fast parsing for RSS feeds
- Handle CDATA sections in `<book_description>` and `<user_review>`
- Parse date strings to JavaScript Date objects, then to PostgreSQL timestamps
- Handle missing/empty fields gracefully (many fields may be absent)
- `<user_shelves>` is a comma-separated string, split into array for database

**Example XML Parser Setup:**

```typescript
import { XMLParser } from "npm:fast-xml-parser";

const parser = new XMLParser({
  ignoreAttributes: false,
  cdataPropName: "__cdata", // Preserves CDATA content
});
const result = parser.parse(xmlString);
```

### Scheduling with pg_cron

[Source: docs/architecture/3-tech-stack-alignment.md]

**Technology:** pg_cron (native PostgreSQL extension in Supabase)

**Configuration:**

- Create scheduled job via SQL migration
- Schedule expression uses cron syntax (minute, hour, day, month, weekday)
- Job calls Edge Function via HTTP request using Supabase internal URL

**Example pg_cron Job Creation:**

[Source: Supabase documentation - Schedule Edge Functions with pg_cron]

```sql
-- First, store Supabase project URL and anon key in Vault (one-time setup)
SELECT vault.create_secret('https://project-ref.supabase.co', 'project_url');
SELECT vault.create_secret('YOUR_ANON_KEY', 'anon_key');

-- Then schedule the cron job
SELECT cron.schedule(
  'rss-ingestion-daily',              -- Job name
  '0 2 * * *',                        -- Cron expression (2 AM UTC daily)
  $$
  SELECT net.http_post(
    url := (SELECT decrypted_secret FROM vault.decrypted_secrets WHERE name = 'project_url') || '/functions/v1/rss-ingestion',
    headers := jsonb_build_object(
      'Content-Type', 'application/json',
      'Authorization', 'Bearer ' || (SELECT decrypted_secret FROM vault.decrypted_secrets WHERE name = 'anon_key')
    ),
    body := jsonb_build_object('trigger', 'cron', 'time', now())
  ) AS request_id;
  $$
);
```

**Required Extensions:**

- `pg_cron`: Scheduling
- `pg_net`: HTTP requests from PostgreSQL
- `vault`: Secure secret storage (Supabase Vault)

**Cron Schedule Recommendation:**

- Daily at 2 AM UTC (low-traffic time)
- RSS feeds update slowly, no need for hourly polling

### Review Date: 2025-09-30

### Reviewed By: Quinn (Test Architect)

### Code Quality Assessment

RSS ingestion handler generally follows the expected parsing/upsert flow, but committing real Supabase credentials and API secrets into the repo is a critical security defect. Cron migration writes those secrets directly into Supabase Vault, so running migrations in any environment will leak and potentially overwrite production secrets. Integration tests currently exercise the live Supabase project using those credentials, which is high risk and couples the suite to production state. XML parsing loop also assumes the feed always yields an array; a single-item feed would throw before processing. Team aligned on shifting to an "env vars + managed secrets" approach, so the remediation plan below reflects that strategy.
